# Presentation workflow

## 1. Cross-source synthesis

Build a thematic matrix across the supplied PDFs and any supporting sources:

- where sources agree;
- where they complement one another;
- where they contradict or use different definitions;
- which source has the strongest evidence for each claim;
- what remains uncertain.

Choose a narrative based on the audience and desired outcome, not on the order in which files were attached.

If the project uses a named conceptual model, keep its terms stable. Map any auxiliary diagnostic or measurement dimensions to that model instead of introducing a competing list without explanation. Mark which ideas come from source documents, public benchmarks, and original teaching design.

## 2. Slide blueprint

Before visual production, define every proposed slide with:

- slide number and purpose;
- one clear thesis;
- supporting evidence, example, or data;
- source and page, section, or URL references;
- planned visual form: figure, chart, comparison, timeline, process, diagram, quotation, or composition;
- speaker-note content;
- any learner choice, pause, or answer reveal, including the intended order;
- relationship to the previous and next slide.

Specify the slide's function in the narrative: orient, create tension, explain, demonstrate, compare, synthesize, or bridge. Write the transition so a viewer can follow why this slide comes next. For narrated work, estimate speaking time from script, pauses, and visual complexity rather than slide count.

Show the blueprint to the user when choices about narrative, audience, brand, length, or sensitive omissions remain unresolved. Do not seek confirmation for routine layout choices already covered by the brief. If revising a deck, add the observed defect and proposed correction for each slide; use the rendered original, not memory of it.

## 3. Content depth

Aim for intellectual density, not crowded slides. Keep the visible layer legible and place nuance, supporting explanation, and secondary evidence in speaker notes or appendix slides. When a source contains essential complexity, split the idea across slides rather than flattening it into generic bullets.

Prefer concrete claims, mechanisms, examples, and numbers over labels such as "benefits", "challenges", or "key insights" without substance.

## 4. Humanizer pass

Run Humanizer only after the evidence ledger and factual wording are stable. Apply it to presentation prose, not to citations, code, formulas, tables, filenames, frontmatter, or machine-readable manifests.

After rewriting, compare every changed sentence against the evidence ledger. Restore any altered number, qualification, causal relationship, ranking, date, proper name, or attribution. Humanizer is a style editor, not a fact source.

## 5. Visual production

Read [visual-design.md](visual-design.md) for the visual audit, composition system, contrast, brand, and asset ledger. Read the installed PPT Master `SKILL.md` before producing an editable deck. Follow its current workflow and validation commands rather than copying stale commands from this reference. If HTML slides are requested, read the installed Frontend Slides skill and [multiformat-production.md](multiformat-production.md) for the second renderer and export contract.

Required visual behaviors:

- use a coherent, content-informed art direction;
- read and preserve the current approved brand manual or template, including its logo rules, typography, fallback fonts, and slide layouts;
- vary layouts according to content while maintaining a consistent system;
- prefer editable native text, shapes, tables, and charts;
- use imagery when it explains, situates, or advances an idea; do not use photographs merely to fill empty space;
- maintain an asset ledger for images, icons, illustrations, and fonts with origin and permitted use;
- avoid repetitive title-and-bullets layouts and decorative filler;
- keep a recurring conceptual model visually stable when applying it to a case;
- keep alternatives visually neutral until the learner has made a provisional choice;
- keep citations readable without competing with the core message.

Use the actual approved identity asset. Do not redraw an unavailable logo by approximation or guess an unconfirmed handle, claim, or presenter detail. Apply recurring identity through the master or layouts without letting it compete with the content.

## 6. QA and completion

Validate the presentation structurally using the current production tools. Render every slide to images and inspect at full readable resolution and in a contact sheet. Keep a short slide-by-slide record of issue, change, and final state. Do not treat a valid package, a zero-error export, or a contact sheet alone as sufficient visual QA.

Check:

- no overflow, clipping, overlaps, broken glyphs, or leftover placeholders;
- consistent margins, hierarchy, typography, contrast, and image quality;
- essential labels readable at the intended display size, with color-independent diagram states;
- charts and tables match source values;
- citations and page references resolve to the evidence ledger;
- all coverage-matrix items have a final disposition;
- speaker notes contain promised nuance;
- each substantive slide has a clear role and a causal, question-based, or contrastive bridge to the next;
- assets have recorded sources and use rights;
- final deck opens and remains editable in an available compatible app; if the intended app is unavailable, report that limit.

Fix defects and re-render changed slides. When a PDF preview is requested, export it from the current editable deck and compare slide order, page count, fonts, and visible content. Use [multiformat-production.md](multiformat-production.md) to distinguish reproducible export from cross-app fidelity. Report separately: source coverage, PPTX validity and editability, rendered preview, visual inspection, notes, PDF export, HTML interaction when present, and limitations.
